## Project status

Blueprint (`bp` CLI) is a pre-alpha Python tool that generates and aligns Power BI PBIP/PBIR report layouts from YAML page specs and a guidelines file. `README.md` is the design doc; everything on its roadmap through v0.8 is built, and every documented guideline key is implemented. The parts: `pbir/jsonfmt`, `pbir/schemas`, `pbir/reader`, `pbir/writer`, `model`, `plan`, `guidelines`, `policies`, `grid`, `validate`, `pbir/formatting`, `bp inspect`, `bp fmt` and `bp check` (including the palette and typography rules). `bp apply` (v0.3): `spec`, `slots` (+ `blueprint/visuals/*.yaml`), `layouts`, `pbir/semantic`, `pbir/ids`, `pbir/registry`, `pbir/render`, `writer.add_create`/`add_modify`. Probe 05 confirmed that Desktop accepts its output as written. Visual types (the core is `slots.CORE_TYPES`, 18 probe-verified types; see Design rules): card, column, header, pie/table/kpi (probe 08 shapes, accepted by Desktop in probe 09; KPI target probe 10, pie drill-down/details probe 11) line/bar (probe 12; line/area drill-down of plain columns, and Desktop's refusal of a second Legend column, probe 27; a drill-down with a Legend draws and several measures with a Legend don't, probe 28), slicer/matrix plus several measures on column/bar/line `value` (probe 20 shapes, accepted by Desktop in probe 21), scatter/multi-row-card/map (probe 34 shapes, accepted by Desktop in probe 36), and stacked-column, stacked-column-100, stacked-bar, donut, area plus the slicer's `options: {style: dropdown}` (probe 22, candidate shapes Desktop drew as written); probe 23 added drill lists, measure lists and donut Details on those, and chart options `labels: on` and `legend: top|bottom|left|right` (bottom: probe 28) (candidates changed on disk and reloaded through the bridge); probe 24 confirmed with a real save that Desktop keeps all of them, as `bp apply` writes them, byte for byte. Option values in contract YAML must be quoted strings (`"on"`, `"off"`: YAML 1.1 reads bare on/off as booleans; `spec._options` maps a spec's bare `on`/`off` back). Spec `options:` are contract-declared formatting literals (`slots.Option`): an option the spec sets is written on creation and rewritten in place when it changes (and noted); one the spec leaves out is left to Desktop (or the user). Bindings: measures, columns, drill-downs, date columns (probe 14) and model hierarchies (probes 16-19, and a matrix's rows and a slicer's field in probes 39-40). ## Architecture

- **Only `blueprint/pbir/` knows the on-disk format.** `pbir/reader.py` builds `model.Report/Page/Visual`. Every model object carries an opaque `source` (a `reader.Document` holding the parsed JSON). The writer patches those documents in place rather than regenerate them, so properties Blueprint doesn't model survive untouched.
- **`pbir/jsonfmt.py` is the only way to read or write PBIR JSON.** It reproduces Desktop's output byte for byte (CRLF, 2-space indent, no trailing newline, raw non-ASCII) and keeps each float's original text via `RawFloat`. Using the stdlib `json` to write will change every file.
- **`pbir/schemas.py`** validates against the vendored Microsoft schemas. Desktop writes minor versions that haven't been published yet (the sample has visualContainer 2.14.0, newest published is 2.13.0). So resolution picks the nearest vendored version with the same major and swaps the `$schema` const. A different major version is unknown. Because a newer minor may add properties the older schema rejects, the writer blocks only on schema errors its own change introduces, and `check` downgrades errors on approximate matches to a per-file warning. When Microsoft publishes a newer schema, vendor it with `scripts/vendor_schemas.py`.
- **`pbir/schema.md` is the source of truth for format facts.** Each fact is marked verified (and how) or open. Don't write code that relies on an open item. Settle it with a Desktop probe and record the result first.
- **Blueprint's own metadata goes in `annotations`** (e.g. `blueprint.ignore`). The schemas reject unknown keys, and annotations are verified to survive Desktop saves, including on visuals Desktop rewrites (probe 01). Never write `pages.json` `activePageName`: Desktop changes it on every save.
- Commands live in `blueprint/commands/`, one module each. `cli.py` only parses arguments. A mutating command changes the model, calls `writer.plan_writes(report)` to get a `plan.Plan` (file writes + warnings), then either prints it (`--dry-run`) or calls `writer.apply`. The writer schema-validates every changed document, refuses files that changed on disk since they were read, writes temp files before renaming any of them into place, and keeps file permissions.
- The writer owns only `position.x/y/width/height` so far. To make Blueprint own another field, extend `writer._visual_write`. Never regenerate a whole document.
- **CI action:** `action.yml` (composite, repo root) installs Blueprint from its own ref into a venv and runs `scripts/ci_check.sh`, which runs `bp check --github` per line of `reports`, writes each text report to the job summary and exits with the worst code. The `action` job in `.github/workflows/test.yml` runs it on the demo. `tests/test_ci.py` keeps `action.yml`'s inputs and the script in step.
- `validate.py` holds the guideline rules (`bounds`, `grid`, `margin`, `gutter`, `overlap`, `page-size`, `density`), pure functions over the model. `gutter` flags visuals that share part of a row or column and are closer than `spacing.gutter` (touching counts; overlaps, diagonal neighbours and `decorative_types` don't). `validate.gutter_gap` is its only definition, shared with `layouts.conflicts`. `bp check` adds `format` findings from `pbir/` (reader warnings plus `schemas.validate_documents`). Rule ids and exit codes are a CI contract, so don't rename them. Rule severities are baked into code (`guidelines.DEFAULT_SEVERITY`); `extensions.severity` overrides them.
- `grid.off_grid_edges` is the only definition of "on grid", used by both `fmt` and `check`. A test asserts that `check` passes everything `fmt` produces.
- `pbir/formatting.py` finds colours by **shape** (`solid.color.expr` anywhere, plus textbox `textStyle.color`), not by property name, and classifies each as `hex`, `theme` (`ThemeDataColor`) or `expression`. Themes resolve through `report.json` `resourcePackages` to `StaticResources/<package>/<path>`. A missing theme is data, not an error. Paths read from report files must never be followed out of the report folder (`_inside_report`).
- The `palette` rule's severity comes from `palette.enforce` (strict/warn/off), not the rule severities. Theme references pass because the theme itself is checked. Textbox colours picked from the theme are stored as resolved hex, so approved shades go in `palette.extra`.
- Typography (`formatting.fonts_in`): roles are `title`/`subtitle` (`visualContainerObjects`), `callout` (legacy `card` `labels` and `cardVisual` `value`, probe 07; chart `labels` are data labels), `card_label` (`cardVisual` `label`, whose theme default is `visualStyles.cardVisual` over `textClasses.label`; `bp theme` writes it there, merging key by key, probe 15) and `textbox` runs. A font weight is part of the face name (`Segoe UI Semibold`), so guidelines use exact face names and `weight` is rejected. A value a visual doesn't write inherits from the theme and is never a violation. Built-in (`SharedResources`) themes may legitimately have no embedded file.
- A guideline key the docs describe but no code implements goes in `guidelines.NOT_IMPLEMENTED`, so `check` reports it as unchecked instead of passing silently. Only check what `schema.md` marks as verified.
- `grid.py` snaps each of a visual's four edges to the nearest grid line, rounding halves up. It skips `blueprint.ignore` visuals silently. It skips, with a warning, pages with no fixed size (`DeprecatedDynamic`) and grouped visuals (group-relative positioning is unverified).

- **Robustness rules (fuzz audit):** report-level files that are unreadable or not JSON objects raise `ReportFormatError` (exit 2). A broken `page.json` or `visual.json` is a warning and is skipped (`reader.load_part`). A visual with a missing or non-numeric position is `positioned=False`, and nothing writes it: the writer would otherwise overwrite it with a placeholder. `OSError` is caught in `cli.main` (exit 2, "nothing was changed"). `writer.apply` removes temp files and any folders it created if writing fails. Malformed-input cases live in `tests/test_robustness.py`. Add to it rather than assuming well-formed files.
- `apply` refuses a layout whose regions are off the guidelines grid, inside the margin or closer than the gutter (`layouts.conflicts`); otherwise `apply` and `fmt` would undo each other forever, or `check` would flag what `apply` built.
- Schema validation dominates run time (about 10 ms per document, even with the shared in-memory registry `schemas._registry`). Don't add validations you don't need. The writer validates "after" first and checks "before" only on errors.

## Design rules (from README; load-bearing)

- Deterministic, byte-identical output. No LLM, randomness or timestamps in the generation path, apart from the manifest's `generated_at`. `bp fmt` must be idempotent.
- Refuse rather than surprise. Never move content between pages or reflow layouts. Honour `blueprint.ignore`. Refuse PBIR-Legacy, and refuse unknown schema major versions unless `--force-schema` is passed.
- **Guidelines schema (template rewrite, v0.6.0):** core keys are `version`, `name`, `canvas` (width/height only), `spacing` (`grid`/`margin`/`gutter`), `page`, `palette`, `typography` and `layouts`; everything else is opt-in under `extensions:` (`severity`, `decorative_types`, `max_resize`, extra typography roles). `typography` has three client roles that `guidelines._typography` maps onto the internal checking roles the rest of the code uses: `page_title`→`header`, `visual_title`→`title`, `body`→`textbox`; `subtitle`, `callout` and `card_label` live in `extensions.typography`. `bold` is gone, which drops a check: for a visual's text a weight is part of the face name, but a textbox run carries its own `fontWeight` (probe 03) and is no longer checked for it; re-add that as an extension rule if it's wanted. Findings and theme notes name the client's key, never the internal role (`guidelines.ROLE_LABEL`/`ROLE_KEY`); `bp describe` reports `spacing: {grid, margin, gutter}`. The pre-template keys (`grid:`, `canvas.margin`/`gutter`, `check:`) are refused with their replacement named (`guidelines.RETIRED`), never ignored.
- **The core 20% (audited 2026-11-11).** The core guidelines file is `guidelines.CORE_KEYS` — one table of section -> sub-keys — and the loader **refuses anything else per layer**, naming the closest real key, so a typo can't load with a default silently (`spacing: {margn: 16}` used to). `extensions:` is the one open section: the core reads five sub-keys and passes the rest through untouched, so an extension never needs a core change. Three sweep tests hold the line: `CORE_KEYS` matches `defaults.yaml`, `template/guidelines.template.yaml` shows every core key, and **no core write-path module names a PBIR visual type** (`test_no_core_write_path_module_names_a_pbir_visual_type`: `render.ACTIVE_BY_TYPE` used to map `slicer`/`pivotTable` to the roles Desktop marks `active`; it is `Slot.active` / `Contract.active_roles` now, declared by each contract). When you add a per-type PBIR fact, put it in the contract YAML, not in Python: the read/check path (`reader`, `formatting`, `validate`) is the exception, because it reads reports no contract describes.
- Config over code. Guidelines YAML never contains conditionals; branching logic is a named policy in `policies.py`. Guideline layers, from lowest to highest priority: `blueprint/defaults.yaml`, then `guidelines/<name>.yaml`, then `<report>/.blueprint.yaml`, then `--set KEY=VALUE` (repeatable; a dotted path, the value read as YAML, so `--set palette.text=#333333` keeps the string YAML would read as a comment). `guidelines.overrides_from` builds that layer, `cli._guideline_flags` adds the flag to every command that reads guidelines, and each command passes it to *every* `guidelines.load` it makes, including the manifest it rebuilds afterwards. The old single-key `--grid` is refused by name (a test pins both).
- No premature abstraction (`create_page()` and `create_visual()` stay separate).

- **Visual types (`slots.CORE_TYPES`):** the archive was a holding pen for the v0.6 refactor, not a permanent split. Everything in it was promoted in batches once its Desktop evidence was complete (slicer/matrix probes 20-21; pie/donut 08, 11, 22-24; area and the stacked charts 22-24 plus probe 35, which evened up their `labels`/`legend` first so the core would behave alike), and **`blueprint/visuals/archive/` is gone**. `scatter`, `multi-row-card` and `map` were then added from probes 34 and 36, so the core is 18 probe-verified types. A scatter's `X` is the one place Blueprint leaves a flag to Desktop: it adds `"active": true` there itself on save, because `active` is a column's drill state and `X` takes a measure. `map` draws only where Desktop's "Map and filled map visuals" security setting is on (off by default; probe 34 needed the user to switch it on). The opt-in machinery stays, for a client's *own* contracts: `extensions.custom_visuals.search_path` in guidelines (anchored to the declaring file, like `layouts.search_path`), or `--visuals DIR` on `apply`/`describe`/`manifest` (layer 4). `contracts(extra)` keys that path into its cache and refuses a type defined twice; every production call site passes `rules.visuals`, because a missing contract silently drops slot names from the manifest. Nothing opts in any more: every probe replay and test runs on the core, and the demo dropped its `.blueprint.yaml` opt-in and stayed byte-identical. A type with no contract is refused by name, so adding one is the only way in. `tests/pinned-specs/` holds a spec a probe was built from (probe 9's `sales-mix.yaml`, which used `pie`): pin a spec there before changing one a probe used.
- **Sort and chart options (probe 31):** a visual's `sort: {by, direction}` writes `query.sortDefinition` **without** `isDefaultSort` — that flag marks only the sort Desktop adds itself, and it doesn't come back when the user sorts to what Desktop would have chosen. `by` must be a field the visual binds. A spec with no `sort` leaves whatever is there (Desktop's default, or the user's). `labels`/`legend` now ship on `bar` and `line` as well as `column`: probe 31 wrote probe 23's shapes onto a clustered bar and a line and Desktop drew and kept them. That made `bar` identical to `column` apart from the PBIR type, so `bar.yaml` is the shipped set's one `inherits:` user; `line` states its own (legend slot, `value` excluding a list beside it).
- **Slot long form (probe 29):** a slot entry may be `{field, aggregate, format}` instead of a string; `"X"` means `{field: X}`. `aggregate` summarises a column in the visual (`sum`/`average`/`min`/`max`, `count` = Desktop's non-null Count = code 5, `distinctcount` = its "Count (Distinct)" = code 2) and is allowed only where the slot takes a measure. `render.AGGREGATIONS` holds each `Function` code with the `queryRef` function and `nativeQueryRef` verb Desktop wrote on a fresh field; `reader.AGGREGATE_FUNCTIONS` holds the same labels so a re-read round-trips (`apply._bound` puts the function where a hierarchy level's name goes, keeping the fingerprint's shape). Two fields Desktop would name alike (count and distinct count of one column) are refused: Desktop adds a digit by hand and that rule isn't verified. `format` is a Power BI format string written verbatim into the projection beside the refs; Blueprint has no `currency` alias because Desktop writes the locale's symbol. A changed format rewrites the query on re-apply, but stays out of the bindings fingerprint (the reader reads it, the mark is what is *bound*).
- **Legend, `legend: off` and table `totals` (probes 32, 33):** `column` (and `bar`, which inherits it) take a one-column `legend` slot (role `Series`, no `active`), with `value` excluding a measure list beside it, as `line` always has; Desktop refuses several measures with a Legend, and two Legend columns, on clustered charts too. `legend: off` writes `legend.show = false`; an option value in a contract may be `{property: show, literal: "false"}` to write a different property of the same object (`slots.Option.properties`), and choosing a value **removes the option's other properties** (`Option.siblings`, `render.with_option(clear=)`), so one option is one state: a legend flipped from `off` to `top` is not left hidden. A fresh visual writes exactly what it did before. `table` takes `totals: on|off` (`total.totals`; Desktop's default is on, so only `off` needs writing). These came from a survey of real reports (counts only: 3 of 6 clustered charts carried a Legend column, 5 of 18 legends were hidden, 2 of 2 tables set totals). Still out of the core, deliberately: axis titles and conditional formatting (zero uses in the survey), and the `map`, `scatter` and `multiRowCard` types real reports use but no contract covers.
- **Specs → placement:** `spec.parse` returns typed `PageSpec`/`VisualSpec`/`FieldRef`. Field syntax: `Table[Column]` is a column and `[Name]` is a measure. `Table[Name]` naming a hierarchy built in the model binds all its levels in order (probe 16), resolved by `apply` against TMDL, and only where a contract's slot accepts `hierarchy` (column, bar, line and pie `category`, table `columns`, and — since probes 39 and 40 — a matrix's `rows` and a slicer's `field`; probes 16-18. A matrix's `columns` still refuses one: no probe has put a hierarchy there. How many levels a well marks `active` differs per well, so the slot says it: `active_levels: first` (the default, a matrix's Rows and every chart's Category — first level `true`, the rest an explicit `false`) or `all` (a slicer's Field), read by `Contract.all_level_roles` and `render._projections`). A hierarchy is one field, so a single-field slot (line `category`) can take one without allowing a column list. Every problem is collected with its location. Visual types are YAML contracts in `blueprint/visuals/`. Only ship a type whose PBIR shape a probe has verified, and cite the probe in the YAML. `layouts.place` fills regions of the matching role in declaration order. Running out of regions is a `LayoutError`, never a reflow.
- `layouts.search_path` entries resolve relative to the guidelines file that declares them (`guidelines._anchor`), not the current directory.
- New object names come from `pbir/ids.py`: 20 hex characters derived from a stable key (never random), so output is deterministic. `pbir/registry.py` is the only code that changes `pages.json` `pageOrder`. The page folder and the registry must change together.

- **`bp apply`** (`commands/apply.py`) finds the pages and visuals it created by the `blueprint.page` and `blueprint.visual` annotations. On a re-run it updates position and title, **rebinds changed fields in place** (`render.with_bindings`: query as for a new visual; Desktop's condition-less auto filters, a sort and `expansionStates` on gone fields cleared; formatting kept; probe 26) and sets spec options (`render.with_option`). Each Blueprint visual carries a `blueprint.bindings` fingerprint of what it last wrote: if the report's fields no longer match it, they were edited in Desktop, and a differing spec is refused unless `--overwrite-edits` (never silently undo a Desktop edit). Visuals made before the fingerprint existed have none and are treated as unedited (nothing is back-filled, so old re-runs stay no-ops). What changed is reported through `Visual.notes`. A page-size mismatch or a changed type is an error. A visual dropped from the spec is kept, with a warning. It never touches hand-placed or ignored visuals, and never deletes. Bindings resolve against the TMDL model (`pbir/semantic.py`, read-only) before anything is written. New documents come from `pbir/render.py`, the minimal shapes from probe 04, and must validate exactly (`writer.add_create`).

- **Spec identity:** a spec's `id` (an explicit top-level `id:`, or the file name) is stored as the `blueprint.spec` annotation on its page. `apply._find_page` matches by spec id first, so renaming `page:` renames the page, and then by page name for pages made before spec ids existed, which get adopted. A page owned by another spec is refused unless `--take-over` is passed. Tests that edit a copy of a spec must keep its file name (or `id:`), or they'll trip this check.
- **Manifest** (`manifest.py`): built only from the model. Anything `apply` knew (layout, region `<role>#<n>`, guidelines `<name>@<version>`) is persisted as `blueprint.layout`/`blueprint.region`/`blueprint.guidelines` annotations so the manifest can be rebuilt from the report. `generated_at` changes only when the content does (`SOURCE_DATE_EPOCH` is honoured). `apply` regenerates it after writing. `check` notes a stale manifest and guidelines drift.

- **Header style:** `typography.page_title` (internal role `header`) is written by `apply` as the header textbox's `textStyle` (probe 03 shapes: `fontFamily`, `fontSize: "20pt"`, `fontWeight: "bold"`). On re-run, `apply` updates the header's text and style if the textbox still has the single run it wrote, and otherwise warns and leaves it. `check` applies `page_title` to Blueprint headers and `body` to all other textboxes.
- **Theme** (`pbir/theme.py`, `bp theme`): `StaticResources/RegisteredResources/blueprint-theme.json` holds only overrides on top of the base theme, the way Desktop saves a customised theme (probe 03): palette → `dataColors`/`foreground`/`background`, `palette.text` → every text class's colour, `typography.visual_title` and `extensions.typography.callout` → `textClasses`, title/subtitle sizes → `visualStyles["*"]["*"]` too, because that level outranks `textClasses` (probe 06), and `extensions.typography.card_label` → `visualStyles.cardVisual["*"].label` (probe 15). Theme defaults resolve as `visualStyles` over `textClasses`, and custom over base (`validate.theme_font`). Replacing a non-Blueprint custom theme needs `--replace-theme`. The old file is kept. `fmt` and `apply` refresh an existing manifest after writing.

## Test data

- `docs/probes/` holds raw diffs from Desktop probes, which are the evidence cited in `schema.md`. Probes are built with `scripts/probe_*.py` on the Windows drive (`C:\Users\<user>\blueprint-probes\`, i.e. `/mnt/c/...`). After the user opens and saves in Desktop, read the diff with `git -C <probe> diff`. The method (README, "How the PBIP format is learned"): write the **predictions in the probe script's docstring before the probe is opened**, build candidates or a `bp apply` page, let Desktop draw and save, then record the result in `schema.md`. A shape written by hand as a candidate (probes 22, 23, 28, 31, 32) says Desktop takes it; only an **acceptance probe** built entirely by `bp apply` (probes 24, 30, 33) says Desktop takes what Blueprint writes, and a feature isn't done until it has both. The user's Windows account name differs between machines, so paths here use `<user>`.
- **Desktop Bridge** (`scripts/desktop.sh`, from probe 21): the bridge CLI runs on Windows Node (the WSL copy reports `UNSUPPORTED_OS`). It can `status`, `reload` and capture a page, nothing else: no save, no UI edits, so a save diff still needs the user's Ctrl+S, and visuals built in the UI still need the user. The Store build of Desktop defeats `open`; open a probe with `cmd.exe /c start "" <win path to .pbip>`, then `status --wait-seconds`. Take page captures rarely (when confused or checking something specific), into `blueprint-probes\_screenshots\<probe>\`, never inside a probe repo. `hasUnsavedChanges` isn't reliable: check file times or `git status` to see whether a save landed. Commit each step yourself with the probe's `snap.sh`. A fresh fixture copy has no data until the user clicks Refresh now, unless you copy an earlier probe's `Fixture.SemanticModel/.pbi/cache.abf` of the same model (gitignored). For the demo (`scripts/demo.sh`), copy `blueprint-probes\_cache\demo-cache.abf` (refreshed and saved by the user on 2026-11-10, demo model incl. the `Order Date` calculated column); probe 19's cache leaves a "calculated columns need to be manually refreshed" banner and stale date data. An untouched open isn't dirty, so Ctrl+S writes nothing; Ctrl+S can be sent with PowerShell `WScript.Shell` `AppActivate(<pid>)` then `SendKeys("^s")` (send only if activation succeeds). Close a finished probe's Desktop with `taskkill /PID <pid>` (graceful); the user wants old instances closed. `screenshot <page-id> --output <png>` takes `--wait-seconds` but **not** `--settle` (only `screenshot-all` does; passing it fails with an empty output folder). A capture taken right after a `reload` can be blank (visuals not yet drawn): `status --wait-seconds`, then capture again before concluding anything. Page ids come from `status`. A fresh `status` right after `open` can show no pages for a few seconds.
- `unverified-probes/` holds probe scripts that have **never been opened in Desktop** (one folder each, predictions written up front, `PROBE = "NN"` to set when it runs). Nothing there is evidence: no contract, `schema.md` fact or commit message may cite a prediction. Its README says what each settles, what is deliberately not probed, and the steps once one has run (record in `schema.md`, write the evidence, move the script to `scripts/`, register the number, then change the contract).
- `samples/` holds real reports for format study. It is gitignored (except its README). Tests reach it through `real_report` (parametrised over every sample present) and `retail_report` (one report's specific facts) in `tests/conftest.py`; both skip when samples are missing. `real_report` globs `samples/*/*.Report`, so only PBIP folders count. A **PBIT** is not a baseline and is not read: its model is TMSL JSON (`DataModelSchema`), not TMDL, its JSON is minified service output, not Desktop's bytes, and probe evidence must come from a PBIP saved by Desktop (to use one, open it in Desktop and save it as a PBIP into `samples/<name>/` without `cache.abf`). The survey method for what real reports use (counts of `queryState` roles and `objects` keys per visual type, never field names or data) is how step 32's features were ranked: do it before proposing a new feature, and only report counts.
- `fixtures/` holds committed PBIP projects built from scratch in Desktop (probe 04), byte-identical to Desktop output, with all content invented. Tests use them through `blank_fixture`/`card_chart_fixture` in `tests/conftest.py`. Never edit them by hand: copy one into `tmp_path` first. `fixtures/README.md` says how to rebuild them.
- `tests/builders.py` builds minimal synthetic PBIR reports in `tmp_path` for edge cases.
- `tests/test_probe_replay.py` rebuilds every probe made on fixture 02 (05 onwards) from its evidence with `git apply`, step by step, and tests Blueprint against Desktop's real output (format, reading, model, rendering, what the user saw, re-apply, fmt, theme). Write evidence with `python scripts/probe_evidence.py <probe folder> docs/probes/NN-name.diff` (byte-exact; hand-made or CRLF-stripped diffs won't replay), and add each new fixture-02 probe to `REPLAYED` (and to `ACCEPTANCE` if Desktop saved what Blueprint built). **Name steps carefully:** the replay treats an evidence section whose title starts with two digits (`01 refresh and save`) as a Desktop save, so a step Blueprint made (a re-apply, a spec edit) must not start with digits: write `blueprint: re-apply …` or `probe NN: spec changed …` (edit the evidence file's `########` titles if `snap.sh` commits made them numbered). Don't give a new module-level helper in that file the name of an existing one: it shadows silently and breaks other probes' tests (`ruff` doesn't catch it).
- Never commit real report files, client measure or table names, or data. `visual.json` and bookmark files can contain data values from the model.
